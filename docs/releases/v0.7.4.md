**The flow percentage was analysed against the reference integration and the captured API
data. The conversion is correct on this hardware** — every one of the owner's six outlets
reports `maximumFlowRate: 200`, which is exactly the condition `byte / 2` requires, and the
live valve words decode to the percentages the diagnostics show (byte 49 → 24.5 %, byte 53 →
26.5 %). No correction was needed there.

**Fixed — the flow slider could not sit still.** Its step was 1 %, but the wire carries
0.5 %: one byte is half a percent, giving 185 positions over the valve's 8–100 % range. Both
of the owner's valves report half-percent values, so with a step of 1 they were off-grid —
the slider could not represent the flow the valve was actually holding, and nudging it
snapped the setting by up to 0.5 % nobody asked for. The step now matches the hardware's own
resolution, which costs nothing: a Home Assistant number still accepts any typed value.

**What the comparison found in the reference integration** (not fixed here — a separate
project):

* It decodes with `flow_byte // 2`, integer division, which **truncates the half-percent**.
  Both of the owner's valves currently carry odd flow bytes, so it would read 24 % and 26 %
  where the valve holds 24.5 % and 26.5 %, and it cannot round-trip an odd byte.
* It never reads `minimumFlowRate` / `maximumFlowRate` at all — no occurrence anywhere in
  either its integration or its upstream library — so its bounds are hardcoded 10–100 % with
  a step of 5, against a true device floor of 8 %.

**The remaining assumption is now documented where it lives.** The Konnect app derives
percent as a ratio against the reported `maximumFlowRate`, so an install with a lower ceiling
would need `byte / (max / 100)`; writing "100 %" on such a device would send double the
intended flow. This integration already reads the real ceiling and already bounds the slider
with it — only the conversion itself still uses the constant. Threading the ceiling into the
encoder is deliberately **not** done blind: it is a no-op on every device in the corpus
(200/100 == 2), so it cannot be verified here, and it writes to hardware that runs water.

**Tests: 38 → 42.** The decode is pinned to both of the owner's real valve words — chosen
because their odd bytes are exactly the case truncation gets wrong — every one of the 185
legal bytes is checked to round-trip, and the slider step is asserted against the wire
resolution on a constructed entity rather than a class attribute.
