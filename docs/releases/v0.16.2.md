**Max Shower Duration now reads `30 min`, not `0:30:00`.** And the question behind "Water Used
This Week" turns out to have been answered too early.

## The display, matched to the app

The value was already in minutes and has been since 0.11.1. What was wrong is that the entity
carried `SensorDeviceClass.DURATION`, which looks like exactly the right class and does two
things this sensor does not want:

* Home Assistant renders duration entities as `H:MM:SS`, so a 30-minute ceiling showed as
  `0:30:00`.
* The class carries a **unit converter**, so the frontend is free to re-express the figure in
  hours or seconds — a 30-minute limit could read `0.5` on someone's dashboard.

The Konnect app, the touchscreen and Kohler's own documentation all say "30 minutes". Matching
the app is the entire reason this entity was renamed from `Rainhead Max Run Time` to
`Max Shower Duration`, and the display is the half that makes it match. The device class is
gone; the stored value and its unit are untouched, so history and automations are unaffected.

The cost is real and accepted: no automatic unit conversion for someone who would rather see
seconds. That is a preference nobody has asked for, weighed against a number everyone reads at
a glance.

## "Water Used This Week" — the earlier answer was not evidence

The honest short answer is that this cannot be built yet, and the reason is more interesting
than it first looked.

`gcs-usage` is the only endpoint that reports real water volumes, and this repo's notes record
`WEEK` and `YEAR` rejected with a generic 400, concluding that `MONTH` may be the only interval
a GCS valve supports. A weekly sensor would need `WEEK`, so that looked settled.

⚠️ **It is not.** Both rejections used the same **400-day window** as the `MONTH` call that
succeeded — and 400 days is roughly **57 weekly buckets against 13 monthly ones**. A server
that caps result rows answers the same generic 400 as one that does not know the interval, so
that test cannot tell "WEEK is unsupported" apart from "that range is too long for WEEK". The
conclusion was drawn from evidence that does not distinguish the two.

`DAY` was never asked at all, yet the MONTH-only conclusion was written as though it covered
every interval.

So `probe_usage` now asks three more questions, designed to separate the causes rather than
repeat the ambiguity:

| Attempt | Buckets | What a 200 or a 400 tells us |
|---|---|---|
| `WEEK iso (90d)` | 13 | The same count `MONTH` serves. A 200 means WEEK works and the old test hit a row cap; a 400 alongside a working MONTH over the same span means the interval really is unsupported |
| `WEEK iso` (400d) | ~57 | Kept as the control — the original call, so the two are read side by side |
| `DAY iso (14d)` | 14 | Never asked before; decides whether "Water Used Today" has a source |

`docs/gcs/api.md` now records the interval support as **open rather than settled**, with the
flaw in the original test written down beside it.

**Run it from Developer Tools → Actions → `kohler_anthem_plus.probe_usage`** against either
shower. It is read-only and changes nothing on the valve.

If `WEEK iso (90d)` comes back with a series, "Water Used This Week" is straightforward and
will follow. If it answers 400 beside a `MONTH` call that works over the same range, then the
valve genuinely serves only monthly buckets — and that is worth knowing as a fact rather than
an assumption, because the alternative is deriving a weekly figure from `totalVolume`, which
this integration has already established cannot be trusted.

**Why it cannot simply be computed:** the monthly series carries one entry per month and no
sub-month resolution. There is nothing in what is already fetched from which a week could be
summed.
