🚨 **One write worked, and then nothing did.** Two symptoms, one bug, mine from 0.18.0.

## What went wrong

Changing a setting succeeded. Then `Default Temperature` **vanished from the dashboard**, and
every subsequent write failed with:

> Refusing to write outlet 0: defaultOutletTemperature, minimumOutletTemperature, outLetFlags
> has not been read from the valve

Both symptoms are the same erasure.

`writeoutletconfig` replaces an outlet's whole record, so 0.18.0 started reading the three
fields nothing had read before — `outLetFlags`, `minimumOutletTemperature`,
`defaultOutletTemperature` — and made a write **refuse** rather than invent one. That guard
worked exactly as intended. What it was protecting against turned out to be this integration
itself.

**The fields were added to the REST parser and not to the MQTT one.** `_apply_outlet_config`
builds a complete `OutletLimits` and *replaces* the stored one, carrying only seven of the ten
fields — so an announcement did not merely omit the other three, it **erased what the REST seed
had read**.

And the trigger is a *successful write*. The valve announces its new outlet configuration
afterwards; that announcement blanked the three fields; the next write refused. One write, then
never again until a reload.

The disappearing entity is the same erasure seen from the other side: with
`defaultOutletTemperature` blanked, `Default Temperature`'s `native_value` became `None`, and
Home Assistant renders a number with no value as unavailable. `Max Temperature` survived
because its own field was one of the seven the announcement *did* carry — which is exactly what
made it look like a fault specific to one entity.

MQTT carries all three, with the write body's key spellings and temperatures already in tenths.
They were simply never read.

## Also made defensive

A field an announcement does not mention now **keeps the value already learned** rather than
being blanked. Every capture carries all ten, but `None` means "not learned" and a write
refuses on it, so depending on that would leave the same one-write-then-never-again failure a
single thin message away.

That one was found by a test rather than by reasoning: the first fix handled the real message
shape and still failed the sparse one.

## What this cost, and what it says

0.18.0 shipped a whole-record write with tests covering the write body, every refusal, the
verification, an ignored write and a partial write — and none of them covered **what happens
to the record between two writes**. The guard that made the failure loud is the only reason it
surfaced as a clear error rather than a silently corrupted outlet record, which is the outcome
it was written to prevent.

Reproduced against v0.18.2 before fixing: it drops exactly those three fields, in exactly the
order the error reported them.

**Tests: 179 → 182**, all three verified failing against v0.18.2 — the erasure itself, the
sparse-message case, and the vanishing entity as the owner saw it.

**Upgrading:** update through HACS and restart Home Assistant. If a setting is currently
refusing to write, the restart alone clears it; this release stops it recurring.
