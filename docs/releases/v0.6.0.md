> ### ⚠️ Breaking — outlet switches are renamed
>
> Every outlet switch whose fixture the valve identifies gets a new entity ID.
> `switch.anthem_valve_zone_1_outlet_1` becomes `switch.anthem_valve_rainhead`.
> **Automations, scripts and dashboard cards referencing the old IDs will stop working
> until updated**, and the old entities remain in the entity registry as unavailable
> until you remove them. The rename is listed in full below.

**Changed — Flow is a control again, on every valve.** It shipped in 0.5.0 as a read-only
sensor, which was the wrong shape: the valve accepts a flow byte and there was no way to
write one from Home Assistant. Each zone now has a **Flow number** — a slider, writing
through the same path the temperature does, so the outlets currently open are preserved and
a change mid-shower takes effect immediately.

**Why it was missing, and why that reasoning did not survive contact with other hardware.**
Flow entities were removed on 2026-08-13 after a first-gen Anthem touchscreen was captured
rewriting *both* zones' flow the instant its flow panel was opened — before any adjustment
was made — applying its own linked scaling and a calibration-derived ceiling. A setpoint
that changes on its own is worse than no control, and on that install the removal was right.

The mistake was the scope. That was **one** install with a particular panel, and the
conclusion was applied to every valve unconditionally, so an owner whose valve honours a
written flow byte had no control either. Flow is the valve's own capability — the codec has
always encoded byte 2 in full, and the write path has always accepted a per-zone flow — so
the control belongs on the valve, and the caveat belongs in its documentation rather than in
place of the entity. On an install whose panel does fight it, disable the entity; nothing in
the protocol layer changes either way.

**The range is the valve's own.** Rather than a fixed 8-100 %, each zone is bounded by the
minimum and maximum flow bytes that zone's first outlet reports — the same pair the Konnect
app bounds its slider with. A valve with flow control disabled therefore offers the narrow
range it will actually honour instead of a full sweep it will ignore.

**Reading it is honest about one thing.** The flow byte is only meaningful while an outlet
is open; on an idle valve it carries a number nobody chose. The 0.5.0 sensor hid the value
in that case, which a control cannot do — a slider that reads `unknown` cannot be dragged —
so the number shows what the valve is holding and flags whether it is live in a
`flow_is_live` attribute.

**Changed — outlet switches are named after the fixture, not the position.** An outlet
called `Outlet 1` says nothing; `Rainhead` says what it does. Where the valve's outlet type
code maps to a confirmed fixture, that name is used:

| Before | After |
|---|---|
| `switch.anthem_valve_zone_1_outlet_1` | `switch.anthem_valve_rainhead` |
| `switch.anthem_valve_zone_1_outlet_2` | `switch.anthem_valve_showerhead` |
| `switch.anthem_valve_zone_1_outlet_3` | `switch.anthem_valve_handshower` |

**The zone prefix is dropped on a single-zone valve**, where there is nothing to
disambiguate and `Zone 1` on every entity is noise. A two-zone valve keeps it —
`Zone 2 Tub Filler` — because a bare fixture name would be ambiguous across zones.

**An unconfirmed type code falls back to the position**, `Zone 1 Outlet 3`, rather than
inventing a fixture name. Only four codes have confirmed meanings; the rest are
install-specific, and a wrong fixture name is worse than an honest number. If your outlets
show a position where you expected a name, the code is one this project has not confirmed —
please open an issue saying what the fixture actually is, and it can be added.

**Two outlets of the same fixture in one zone keep their positions** — `Showerhead 1`,
`Showerhead 2`. A pair of body sprays or two showerheads on one zone is a legal
installation, and naming both the same would have built one entity ID twice, which Home
Assistant resolves by silently dropping the second: an outlet would simply not exist, with
nothing in the log to explain it. Only a repeated fixture is numbered; a unique one stays
plainly `Rainhead`.

**Names are read once, at startup.** Per-outlet types arrive gradually over MQTT and from
the REST seed, so a valve that has not announced its outlets yet names them by position and
picks up fixture names on the next restart. Renaming entities while Home Assistant runs
would change their IDs underneath whatever automations are using them, which is worse than
waiting for a restart.

**Removed — the read-only Flow sensor from 0.5.0**, replaced by the number above.

**Upgrading:** update through HACS and restart Home Assistant. Then, in order:

1. **Update anything referencing an outlet switch** — automations, scripts, dashboard cards,
   template sensors. The table above lists the renames for a single-zone valve; a two-zone
   valve keeps its `zone_N_` prefix.
2. **Remove the old entities.** They stay in the registry as unavailable; delete them from
   the valve's device page.
3. The Flow numbers appear as new entities, one per zone. The 0.5.0 Flow sensor is gone.

No config changes, and nothing else is renamed — temperature, status, and the diagnostic
entities keep the IDs they had.
