**Added — Flow, Total Water Used and System State, on every Anthem valve.** Three readings the
valve has been sending all along and the integration was throwing away. Nothing new is asked of
the cloud: all three ride on the `GCS_SOLO_STS` message the stream already receives, so they
cost no extra call and update the moment the valve speaks.

**Flow** is the commanded flow as a percentage, and it reads `unknown` whenever water is not
actually moving. That is deliberate, and it is the whole reason this entity took care to build:
the flow byte is only meaningful while an outlet is open. On an idle valve it carries a number
nobody chose — 296 words in the capture corpus read a flow other than 100 % with nothing open,
in recurring pairs like 34.5 %/82.5 %. Publishing that would put a flow reading on your
dashboard for a shower that is not running. The raw byte is still on the Zone 1 Hex sensor's
`flow_percent` attribute, beside the `flow_is_live` flag that governs this entity.

**Total Water Used** is the lifetime total from `totalFlow`, in gallons or litres to match the
account, and marked `total_increasing` so it feeds the water dashboard and long-term
statistics. **It is filtered, and it has to be.** The valve emits an occasional frame where
`totalFlow` collapses to near-zero and is back at its previous value seconds later — three
times on separate days in the corpus:

```text
19:18:06  totalFlow=1656   water off
19:20:05  totalFlow=2      <- the glitch frame
19:20:07  totalFlow=1653   back, seconds later
```

Published raw, one such frame tells Home Assistant the meter was replaced and injects a phantom
spike the size of the whole counter into long-term statistics, which cannot easily be undone
once recorded. So a reading that drops below half the last accepted one is held back — but
**only once**: a genuine counter reset arrives as a collapse too, and rejecting it for ever
would freeze the sensor at a value the device has stopped reporting. Two low readings in a row
are taken as real. A glitch costs nothing; a real reset costs one frame of delay. The count of
suppressed frames is on the entity as `glitch_frames_ignored`, and both raw counters are in
diagnostics, so the filter can be checked rather than trusted.

**System State** is the valve's own `currentSystemState` — `normalOperation` or
`showerInProgress`. It is a **second opinion, not a restatement of Status**: `Status` is decoded
from the command word, this is a flag the valve sets for itself, and when the two disagree that
disagreement is the useful signal. A firmware that adds a third state reads `unknown` here and
names the real string in the entity's `reported` attribute, rather than logging an error on
every update.

**Added — a Problem binary sensor on each valve, and it is not hidden.** Reads the status word's
`errorFlag` from either zone, as a standard `problem` device class. Almost everything else
diagnostic in this integration is disabled by default; this one is not, because a fault the
owner cannot see is the one case where a hidden entity is worse than a visible one.

This reverses an earlier decision, and the earlier reasoning was sound: the bit has **never been
observed set — 0 of 992 captured valve words** — and publishing a detector nobody has been able
to test claims more than the evidence supports. What changed is the weighing, not the evidence.
Its cost when wrong is a false "OK", which is exactly what an owner without the entity already
has; its value when right is the only warning this integration is able to give. So it ships with
the caveat attached rather than in place of the entity: the sensor publishes
`fault_detection_verified: false`, and per-zone `error_codes` ride along as attributes. Byte 7
reads a constant `1` on the tested unit, so a nonzero code is **not** a fault — the flag is the
only fault signal. **If you ever see this turn on, please open an issue with diagnostics
attached.** It would be the first captured fault, and it is what the entity is waiting for.

**Changed — the Favourite picker says why it is empty.** An `Off`-only dropdown is
indistinguishable from one that failed to load, and the difference matters, because usually
nothing is wrong: a GCS valve has **ten preset slots**, slot 1 is the mandatory default shower —
run by the Shower switch and hidden from the list, exactly as the Konnect app hides it — and the
other nine are empty until somebody creates a favourite. So a valve nobody has customised
correctly offers nothing, and now says so in a `no_favourites_reason` attribute naming the cause
and the fix. Create a favourite in the Konnect app and it appears with no reload.

**Changed — experiences are named instead of silently omitted.** The picker has always excluded
experiences, because they carry no valve settings and the shower ignores the command — correct,
and independently confirmed by a separate reverse-engineering of the same hardware. They are now
named in the entity's `experiences` attribute with an `experiences_note` saying why they cannot
be started, and an automation that names one by mistake gets an error that says so rather than
"no such favourite". They are still **not** added to the dropdown: an option that raises the
moment anyone picks it is worse than an option that is not there.

**Fixed — the preset counts in diagnostics could not be read straight.** `selectable` counts
slots before the hidden default-shower slot is removed, while the dropdown offers what is left
after — so a valve with no user favourites reported `selectable: 1` and offered nothing, which
reads as a bug and is not one. This was mistaken for exactly that during development. The report
now carries `offered` beside `selectable`, plus `hidden_ids_present`, so the two numbers can be
told apart.

**Fixed — diagnostics downloaded from the second valve described the first.** The report has
always carried every device, and still does. But the singular `valve`, `endless_shower` and
`warmup` blocks were hardcoded to the first valve while `requested_for` correctly named the
button that was pressed — so a report downloaded from the second valve's page read
`requested_for: valve_1` above a block describing valve 0. On an account whose valves differ in
exactly the fields those blocks are read for — a 30-minute and a 60-minute run-time limit, on
the account that found this — the full picture was present in `valves` and the label was the
lie. That is the failure this module exists to prevent, so the singular blocks now follow the
device whose button was pressed. Same for `controller`. A report from a single-device account,
and one from the integration card, read exactly as they did.

**Changed — diagnostics gain the new readings.** `system_state` sits beside the decoded
`is_running`/`is_paused`, so a disagreement between them is visible in a bug report, and a
`water` block carries the raw and published totals with the count of suppressed glitch frames.

**Changed — the Valve picker on `custom_shower` and `send_valve_hex` appears only when there is
more than one valve.** With a single valve there is nothing to choose, so the field is not
shown, just as Zone 2 is not shown on a single-zone valve. This shipped in 0.4.1; it is listed
here because 0.4.1 was a documentation release with no HACS build, so this is the first release
to carry it.

**Beta, and honestly so.** The three new readings are decoded from captured data and verified
against it, including the glitch sequence above; the Problem sensor has been built and checked
but not exercised on live hardware, and the fault detector is untestable by construction until
a fault occurs. Please open an issue with how they behave on yours, with diagnostics attached.

**Upgrading:** update through HACS and restart Home Assistant. No config changes to make. The
new entities appear after the restart — Flow, Total Water Used, System State and Problem, on
each Anthem valve. Nothing is renamed or removed, and no existing entity changes its ID.
