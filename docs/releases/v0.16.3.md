**`WEEK` is supported after all.** The owner pointed out that the Konnect app shows weekly
statistics — which settles in one sentence what two probe results had been read as proving the
opposite.

## What was wrong, and why the evidence never said what it was read as saying

0.16.2 shipped a day ago saying a weekly sensor could not be built because `gcs-usage` rejected
`Interval=WEEK` with a 400. That was an accurate report of a test result and the wrong
conclusion drawn from it.

The app shows weekly stats on this same account and this same hardware. It reaches this
endpoint through `getAnthemWaterUsageData`, and its week tab sends `Interval=WEEK` — the
`tab_week` const-string recovered from `WaterUsageViewModel` and recorded in
`docs/gcs/api.md` since 0.7.8. **A feature visible in the app is proof the API serves it.** No
probe result outranks that.

The test could never have shown otherwise. `WEEK` was asked over the same **400-day window** as
the `MONTH` call that succeeded — and 400 days is roughly **57 weekly buckets against 13
monthly ones**. A server that caps result rows answers with exactly the same generic 400 as one
that does not recognise the interval. "WEEK is unsupported" and "that range is too long for
WEEK" were never distinguishable in that evidence, and the conclusion went past what the test
could support. `DAY` was never asked at all, yet was covered by the same conclusion.

⚠️ **This is the second time this endpoint has been called unsupported on evidence that could
not support it.** The first was the camelCase probe of 2026-09-10, where fifteen candidates
returned an identical 400 — including a bare call — and the uniformity was the clue that
nothing was being recognised as a parameter at all. Both times the failure mode was the same:
one generic error standing in for several different causes.

## What now gets asked

`probe_usage` asks `WEEK` over **three** ranges, so the result locates the constraint instead
of merely re-confirming it:

| Attempt | Weekly buckets | Why |
|---|---|---|
| `WEEK iso (28d)` | 4 | About what the app's week tab displays — the shape most likely to match what the app actually sends |
| `WEEK iso (90d)` | ~12 | The same bucket count `MONTH` is known to serve |
| `WEEK iso` (400d) | ~57 | The original call, kept as the control so the three are read side by side |

Where those diverge is the answer. `DAY` over 14 days is asked beside them on the same
reasoning.

**Run it from Developer Tools → Actions → `kohler_anthem_plus.probe_usage`** against either
shower. It is read-only and changes nothing on the valve. Attach or paste the result and
`Water Used This Week` follows directly — the monthly sensor already does all the surrounding
work (litres on the wire, the account's unit for display, `TOTAL` rather than
`TOTAL_INCREASING`), so what is missing is only the range that the cloud will answer.

`docs/gcs/api.md` now records `WEEK` as **supported**, with the flaw in the original test
written down beside it rather than the conclusion it produced.

**Tests: 164**, with the probe's range coverage asserted so a future edit cannot quietly drop
back to a single ambiguous call.
