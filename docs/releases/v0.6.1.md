**Fixed — the rainhead outlet was not named.** Two of the three outlets on a K-28210 picked
up their fixture names in 0.6.0 and the first stayed `Zone 1 Outlet 1`. The fallback worked
exactly as designed — an unconfirmed type code is published as a position rather than given
an invented name — but the code should not have been unconfirmed.

**A rainhead is type `31`.** The map shipped in 0.5.1 said `62`, and `62` is not a code that
install reports at all. Its outlets read `31, 11, 1`; the second and third are Kohler's own
documented codes for a showerhead and a handshower, which is what makes the first credible.

**How `62` got in there, because the mistake is worth naming.** It was inferred by assuming
a second install's outlets sat in the same id order as the reference machine in this
project's capture corpus — outlet 1 is id 0, the corpus says id 0 is type `62`, therefore
`62` is a rainhead. The reasoning looked sound because the *third* outlet independently
matched the documented `1 = handshower`, which was taken as confirming the whole row. It
confirmed only that one position. The corpus codes belong to a different set of fixtures,
and `52` went the same way.

**Codes are now added only on a direct report of a valve's own numbers**, never by lining
two installs up against each other. `52` and `62` are removed from the map and returned to
the unconfirmed list alongside `38` and `39`. If your outlets show a position where you
expected a fixture, please open an issue with the `outlet_type` attribute from that switch
and what the fixture actually is.

**Added — a Registered sensor, the install date that turned out to exist.** 0.5.1 reported
that no date field appears anywhere in the API. That was wrong: the `gcs-configuration`
record 0.5.1 itself added a read of carries **`createdTime`**, which the summary in
diagnostics was reporting by name only — so the answer was sitting in the report, unread.

It is **when Kohler's cloud created the device record, not when a plumber fitted the
valve**, and the entity is named for what it is rather than what it approximates: a valve
replaced under warranty or re-registered after a service call reads as newer than the
plumbing. For most systems the two are within a day of each other, which is what makes it
worth having. Diagnostic and disabled by default; enable it from the valve's device page.
Diagnostics now carry the value rather than just the key name.

**Answered — a controller-free install populates none of the structural fields either.**
This project has carried an open question about whether `gcs-configuration`'s `zoneone`,
`zonetwo`, `parts`, `valve1Settings`, `valve2Settings`, `systemConfiguration` and
`systemSettings` are populated on a valve with no Anthem Plus controller. A report from
exactly that account, running 0.5.1, says **all seven are null there too** — so the nulls
are not the controller shadowing the valve, and `gcsadvancestate` remains the only source
for outlet topology. The `about` block is absent entirely on such an install, which is why
the Firmware sensor added in 0.5.1 reads `unknown` there.

**Upgrading:** update through HACS and restart Home Assistant. Outlets whose fixture is now
recognised are **renamed again** — `switch.anthem_valve_zone_1_outlet_1` becomes
`switch.anthem_valve_rainhead` — so anything referencing the position ID needs updating, and
the old entity stays in the registry as unavailable until removed. This affects only outlets
that 0.6.0 left named by position; those already named in 0.6.0 keep their IDs.
