**`Warmup Auto-Restore` is no longer created on an account with no Anthem Plus controller.**

## Why

The switch exists for one fault: the valve's warmup mode does not stay where it is put,
because **the Anthem Plus controller's web UI writes `warmUpDisabled` to the valve as a fixed
step of its signed-in routine** — established after six live reproductions in a day, and
recorded in [`gcs/api.md`](../gcs/api.md) §3h.

That write originates in the **hub's** firmware. The valve is only the recipient.

On a controller-free account, every `warmUpDisabled` in the whole capture corpus traces
either to that routine or to a post-reboot restatement where the mode did not actually
change. There is no known cause of a spontaneous disable on such a system — so the switch
defends against nothing observed, and turning it on could only add an unprompted writer to
the valve.

## What changes for you

Nothing, unless you had deliberately turned it on. It shipped **off by default** with a
`hub_present` attribute reporting exactly this conclusion, so the honest version is not to
create it at all.

An account that pairs one valve with a controller and leaves another valve standing alone
keeps the switch on the first and loses it on the second. The retired row is therefore
purged by **device id, not by suffix** — the blanket `_REMOVED_UNIQUE_ID_SUFFIXES` list
would have taken it from both. Like the zone purge in 0.19.0, it runs as cleanup that can
never fail setup: a stale registry row is cosmetic, the entities the platform exists to
create are not.

If you *had* enabled it, the mode it would have restored is still remembered in the config
entry's options. That is harmless, and it means adding a controller later resumes with the
target intact.

## Tests

186, unchanged. The existing `hub_present` test was rewritten rather than added to — its
premise is now expressed by the entity's absence rather than by an attribute — and verified
failing against 0.19.0 first.
