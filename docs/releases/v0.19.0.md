⚠️ **Two entities renamed, and one removed from single-zone valves.** Automations and
dashboards referencing them need updating — see **What to change** at the bottom.

## `Status` is now `System Status`

On both devices. System-level is what it is: warm-up and pause are properties of the whole
valve on this hardware, not of a zone, so there was never a per-zone `Status` this could be
one of.

**The unique ids are unchanged.** A rename that moved them would have orphaned every
automation and all recorded history, so Home Assistant keeps the same entity ids unless you
have customised them yourself. There is a test pinning exactly that.

## `Shower Active` is gone on single-zone valves

It answered the question `Status` already answered. On a K-28209 or K-28210 there is one
zone, so "this zone is flowing" and "the system is running" are the same fact — and the
binary said strictly *less*, because it excluded warm-up and reported a pause as simply off.
It was a worse copy of a row already on screen.

**Multi-zone valves keep one per zone**, where `System Status` genuinely cannot help. Pause
and warm-up are system-level, so there is no per-zone `System Status` to split it into, and
only these say *which* zone is running. They are `Shower Active 1` and `Shower Active 2`.

### The countdown moved rather than went with it

`flowing_for_seconds` and `seconds_remaining` are now attributes of `System Status`.
`seconds_remaining` is the number that matters mid-shower — how long before the valve's own
run-time limit closes the water — and nothing else publishes it, so it had to outlive the
entity that carried it.

It takes the **soonest** cutoff across zones: with two zones running, the first one to stop
is the one worth warning about, and a maximum would promise time one of the showers is not
going to get. It stays `None` — never `0` — when the limit is unknown, when nothing is
flowing, or after a reconnect, because the detector drops its timings across a gap rather
than reporting a duration it cannot stand behind.

## `Shower Active` is no longer diagnostic

It was categorised diagnostic *with* an enabled-by-default override undoing half of that
categorisation, plus a comment explaining the exception — which is the shape of a
miscategorised entity rather than a considered one. On the multi-zone valve it now exists
on, "which of my two showers is running" is primary state, the same kind of fact as
`Temperature 2`, not an aid to debugging one.

## The retired row is purged by device, not by suffix

The existing `_REMOVED_UNIQUE_ID_SUFFIXES` list is unconditional, and `_zone_1_active` has
to **survive** on a multi-zone valve. The zone count is only known once the coordinator has
read the model, which is after that blanket purge runs — so this one matches the valve's own
device id instead. An account with a single-zone valve and a two-zone valve purges the first
and leaves the second alone.

It is also cleanup that can never fail setup: a stale registry row is cosmetic, and the
entities the platform exists to create are not.

## What to change

| Was | Now |
|---|---|
| `sensor.anthem_valve_status` | `sensor.anthem_valve_system_status` |
| `sensor.anthem_plus_status` | `sensor.anthem_plus_system_status` |
| `binary_sensor.anthem_valve_shower_active` | `sensor.anthem_valve_system_status` is `Water Running` |

The entity ids follow the names automatically unless you have customised them. The last row
is the one to look at: on a single-zone valve that entity no longer exists. Its replacement
is **not** an exact swap — `Water Running` excludes warm-up exactly as the binary did, but
`System Status` also distinguishes `Warming Up` and `Paused`, which the binary collapsed
into "off".

## Also in this release

**Sparse zone messages no longer blank the controller's readings.** Found by sweeping for
the *same class* of bug as 0.18.3 rather than assuming it was isolated: `_apply_valve`
rebuilds a whole `HubZone` and replaces the stored one, so a message without `temperature`
or `flowrate` erased what an earlier one reported — and the zone temperature sensor goes
unavailable on a `None`, which is the same disappearing-entity symptom from the other side.

Latent rather than active: every captured `SHOWER_VALVE_STS` carries all four keys. Fixed
anyway, because that stream is documented as coalescing snapshots and skipping windows, and
"every message we have seen carries it" is precisely the assumption that caused 0.18.0
through 0.18.2. Affects controller owners only.
