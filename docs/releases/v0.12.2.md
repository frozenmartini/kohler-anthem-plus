Scoping correction: **warm-up auto-restore is a fix for a hub fault**, and the documentation
presented it as a general hazard.

## The disable comes from the hub, not the valve

`docs/gcs/api.md` §3h establishes the cause of the spontaneous warm-up disables in detail —
ordinary signed-in use of the Anthem Plus controller's web UI writes `warmUpDisabled` to the
valve as a fixed step of its routine, a PIN sign-in alone being enough, reproduced live six
times in one day.

Every word of that is about a **hub-attached** installation. The write originates in the
controller's firmware; the valve is only the recipient. But the user guide described it as
something that happens to *valves*, without saying a controller is required for it to happen
at all — so an owner of a valve-only system would read it as a risk they were exposed to.

**No cause is known for a controller-free account.** Every `warmUpDisabled` in the corpus
traces either to that hub routine or to a post-reboot restatement where the mode did not
actually change. On such a system this switch defends against nothing observed, and enabling
it only adds an unprompted writer to the valve.

The switch now publishes **`hub_present`**, which is the attribute that answers "is this worth
enabling here" — `false` means the fault it exists for cannot occur on this account. The user
guide and the switch's own documentation say so too.

If anyone does see a spontaneous disable on a valve-only system, that is a new observation and
worth reporting: it would be the first.
