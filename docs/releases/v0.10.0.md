The three findings v0.9.0's audit ranked below what it fixed, plus the refactor that audit
flagged and left alone. No behaviour changes on a healthy system — this is entirely about
what happens when something is not healthy.

## Malformed cloud payloads no longer break setup

Every REST seed walked the response with `payload.get("state") or {}`. That rescues a *null*
`state`, which is the case anyone writes the line for — but it passes a wrong *type* straight
through, and the next `.get` raises `AttributeError` inside the seed. A list, a string, or a
number where an object belonged would fail setup with a traceback rather than a message.

None of that needs a hostile cloud: a schema change, a truncated response, or an error body
shaped like a success produces exactly these shapes. Both seeds — `gcs-state` and `hub-state`
— now type-check every container before walking it, and skip what does not fit rather than
raising. Falling back to the pre-seed defaults is the honest response: MQTT is authoritative
and corrects anything the seed misses on the next message.

Two of the nested reads were wrong in a quieter way. A `shower` entry that was not an object
would raise inside `zone_number`, which reads five different spellings off it. And an
`outlets` value arriving as `"111"` instead of `[1,1,1]` was indexed positionally — the string
decomposed into truthy characters and read as **every outlet running**, with no error
anywhere. Both are now checked.

## Preset words are validated before being echoed back

`writepreset` replaces a preset record whole, so every field the integration is not changing
has to be sent back exactly as it was found — including each valve's `hexString`, a value the
integration never computed. That is a narrow trust boundary but a real one: a preset word
carries the same 10-bit temperature the command word does, so a corrupted record could hold
102.3 °C and this integration would be the thing that wrote it to the valve.

Stored words are now decoded and checked against the same 48.8 °C ceiling `encode_preset_word`
already clamps to — so a word this integration wrote always passes, and only a foreign one can
fail. A word that fails is dropped with a warning rather than echoed, which sends an empty
field for that valve: exactly what an unused valve already gets. The failure mode is a preset
that stops driving one valve, not one that runs it too hot.

## Warm-up moved out of `Valve`

`Valve` was 1,914 lines and 66 methods, and a fifth of that was one setting. Warm-up needs
more machinery than a setting normally does — a memory of the last enabled mode, a record of
our own writes so a restore does not fight itself, a delay-and-recheck before writing, a
counter that gives up rather than fight forever, and a journal of the whole thing because the
cause is still an open question — and all of it was interleaved with everything else the valve
does.

It now lives in `warmup_manager.py` as a closed system: thirteen methods and six pieces of
state, reached from the rest of the valve through four members. `Valve` is down to 1,455 lines
and 60 methods. Thirty lines of warm-up reasoning that sat in the middle of `async_seed` — a
method about seeding everything *except* warm-up — moved with it.

**Nothing about this is visible from outside.** `warmup_auto_restore`, `last_warmup_mode` and
`async_set_warmup` still work and still mean the same thing; entities, services, diagnostics
and unique ids were not touched.

One bug was found *by* the move and fixed in it: the warm-up journal's baseline record still
called a method that had moved, which would have raised on every log open. There is now a
static test that fails if any call site in `Valve` names a member `Valve` does not have —
verified against the bug it was written for.
