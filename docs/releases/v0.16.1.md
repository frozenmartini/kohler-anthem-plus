**Max Shower Duration read `unknown` while it knew the answer.** Reported by the owner the
day 0.16.0 shipped, and the fix is one character.

## The value was right the whole time; reading it was what failed

`Valve.outlet_run_times` is **1-based** — it maps its 0-based internal store up by one, and
its docstring says so. The code that builds this sensor's attributes added one *again*. So
every outlet was looked up one place too high, and the last one ran off the end of the model:
`outlet_location` raises `ValueError` for an outlet a valve does not have.

Home Assistant reads a sensor's state and its attributes together. An exception in either
fails the entity, so the state never reached the state machine — and the sensor showed
`unknown` while `native_value` was returning `30` on every single update.

This was verified rather than inferred. A diagnostics download taken minutes before the fix,
on 0.16.0, showed both of the owner's valves as **K-28210, all three outlets learned at
1800 s, nothing awaiting a run time, MQTT connected**. Everything the sensor needed was
present and correct; `outlet_location(4)` on a three-outlet valve is what stood between that
data and the dashboard.

⚠️ **Two mistakes had been cancelling each other out.** `make_valve` built `outlet_run_times`
with `range()`, handing entities 0-based keys that no real valve produces, and both duration
tests passed 0-based keys inline to match. Against that fixture the extra `+ 1` looked
correct — it was compensating for a fixture that was itself wrong. That is why a `ValueError`
on real hardware survived a test suite that covered this sensor. The fixture and both tests
now use the 1-based keys the property actually returns, and the new test fails against 0.16.0
with exactly the error the owner's hardware hits.

If this sensor has been `unknown` on your system, it will populate on restart. Nothing else
changes: `Endless Shower` was reading the same numbers directly and was never affected, so
the cutoff feature was armed correctly throughout.

## Asking whether daily water data exists

A request to expose water used *today* has no source yet. `gcs-usage` is the only endpoint
that reports real water volumes, and this repo's own notes record `WEEK` and `YEAR` both
rejected with a generic 400 on the owner's account, concluding that `MONTH` may be the only
interval a GCS valve supports.

**But `DAY` was never asked.** The probe tried `MONTH`, `YEAR` and `WEEK`; the conclusion
covered the three that were tested and quietly generalised to a fourth that was not.

So `kohler_anthem_plus.probe_usage` now tries `DAY` over a 14-day window — a short range on
purpose, because 400 days of daily buckets is a large response for an exploratory call, and
an interval that works at all works over two weeks. It is one read-only GET and changes
nothing on the valve.

Run it from **Developer Tools → Actions** against either shower. If `DAY iso (14d)` returns a
series, "Water Used Today" becomes straightforward. If it answers 400 like its siblings, then
daily data does not exist in this API — and that is worth knowing as a settled fact rather
than an assumption, because the alternative is deriving a daily figure from `totalVolume`,
which this integration has already established cannot be trusted.

Also: the probe's placeholder values are now shared with the test that checks every candidate
renders, rather than the test keeping its own copy. A placeholder added to a candidate and
not to the substitutions is a `KeyError` against live hardware — the one failure mode that
test exists to prevent, and one a duplicated dictionary cannot catch. It caught this
release's addition.

**Tests: 161 → 162**, the new one verified failing against 0.16.0.
