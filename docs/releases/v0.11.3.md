Two corrections found by reading a real diagnostics download, both of which had been asserted
as facts in comments for months.

> ⚠️ **Superseded by 0.11.4.** The behaviour below is correct, but the explanation is not:
> outlets are *not* configured with different run times. A mixed set is a **lost write** —
> there is one master duration, written one outlet at a time, and one of the calls did not
> land. See the 0.11.4 notes.

## Outlets do **not** all report the same run time

`Max Shower Duration` read outlet 1 alone, on the documented reasoning that "every outlet
observed on this install has agreed". That is no longer true, and the evidence is one of the
owner's own valves: **1800 s on its Rainhead and Handshower, 3600 s on its Showerhead**, in a
single zone.

So the entity reported 30 minutes on a valve that would run one fixture for 60. It now reports
the **shortest** — the soonest the water can actually stop, which is what someone reading a
maximum duration is planning around — and publishes the full breakdown:

* `per_outlet` — every outlet's limit in minutes, named the way the outlet is named elsewhere
* `outlets_agree` — `false` on a valve like the one above, so the disagreement is visible
  rather than averaged away

**The run-time cutoff feature was already correct.** `Valve._zone_limits` has always collected
every distinct value as a candidate rather than picking one, exactly for this case. Only the
sensor and the comments were wrong.

## The scald limit reaches diagnostics

`maximum_temperature_tenths` was added to `OutletLimits` in 0.11.1 but never to the diagnostics
report — so the first reports carrying the new `Max Temperature` sensor could not distinguish
"the valve did not send it" from "the parser missed it", which is the one question such a
report exists to answer. It is now reported per outlet.
