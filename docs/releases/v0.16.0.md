Three passes over the whole integration — performance, maintainability, then security. Four
privacy gaps closed, one of them live on any account with more than one valve.

## Your device ids were back in the log

**Three INFO messages had reintroduced them.** 0.9.0 took device ids out of the startup line
and out of every read error, because a Kohler device id is not merely an identifier — it is
the address the cloud uses to reach your valve, and `home-assistant.log` is the file people
paste into issues. Three messages added since then put one back: both topology-mismatch
messages, and the per-valve settings migration.

**The topology messages are the ones that matter**, because the condition that triggers them
is having more than one valve whose layout differs from the entry's — which is exactly the
account those messages exist to serve. All three already name the device, so the id was
telling a reader nothing they did not have. A static test now holds the line, allowing only
`mqtt.py`'s deliberate last-eight-characters of *this integration's own* mobile registration,
which is not a device address.

## Three that were latent rather than live

Reported honestly as what they are: none of these had leaked anything on the owner's account.
They are gaps in guarantees that this integration states elsewhere, found by testing the
guarantees rather than reading them.

**The diagnostics version scanner could have copied out an identifier.** It takes any value
whose *key* names a version, guarded by a 24-character ceiling — on the stated grounds that
"a device id, serial or GUID is not" short. A real Kohler device id is `gcs-sio32343h7`:
**fourteen characters**. The ceiling could never have caught one. No captured payload has a
version-shaped key carrying an id, and that is the point — this scanner exists precisely to
walk fields no capture has covered, on accounts unlike the owner's. The value's shape is now
checked as well as its length. Every real firmware still reports, including the bare integer
`10` the app shows for the valves.

**A secret can hide in a value under an innocuous key.** The API probe log redacts any key
whose name looks like a password, token or secret — which is the right rule for the fields
Kohler is known to return, where the SAS token arrives under `password`. But an Azure
connection string carries the whole credential *inside one string*, under the name
`connectionString`. That matters because this runs on whatever the cloud returns, including
`probe_usage`, which deliberately calls undocumented endpoints. Values are now checked too.

**The report log would have resumed outside its directory.** The episode name is joined
straight onto the log folder, so a name containing `..` writes elsewhere. Only `start()` ever
writes that name, from its own timestamp, so a hostile value means the config entry was
already edited — at which point far more is available than this. Guarded anyway: the value
round-trips through a file an operator may hand-edit, and the check is one comparison.

## Startup is two round trips deep instead of five

A valve's seed makes five REST calls, and only one ordering among them is real: `gcs-settings`
carries the outlet topology, and `gcs-state` cannot be decoded until that has been applied.
`gcs-configuration`, `gcs-usage` and `gcs-preset` depend on neither that nor each other, but
were issued after the pair anyway.

They now start before it and are collected after. **0.506 s → 0.203 s per valve** at 100 ms
per round trip, so roughly 0.6 s off every cold start and reload on a two-valve account. The
call count is unchanged at 14 for a one-valve, one-controller install; what changed is how
much of it is spent waiting.

⚠️ **Cancellation was the subtle part.** A reload mid-seed cancels the coroutine, and an
`await` inside a plain `finally` is cancelled along with it — which would leave those reads
running against an entry that is going away. That is the same class of bug 0.15.1 fixed for
the reconnect reseed, so the background task is cancelled explicitly and reaped before the
error is re-raised. Verified at zero orphaned tasks.

## One duplicate worth removing

`_word` — zone number to that zone's command word — was declared identically in the number
platform and the hex sensor. Worth sharing not for the five lines but for the failure mode:
**reading the wrong zone raises nothing**. A two-zone shower would report and command the
other half, silently. Both now take it from `ZoneWordEntity`.

Entity ids are unchanged; that was verified on a real instance rather than assumed, along
with the hex sensor's diagnostic category, its disabled-by-default state and its icon.

## What the passes found already correct

Reported because they were verified, not skipped. TLS verification is never weakened —
`create_default_context`, confirmed at `CERT_REQUIRED` with hostname checking and a TLS 1.2
floor. No `eval`, `exec`, `subprocess` or `pickle` anywhere. No user input reaches any
generated filename. Path redaction is correct on every real endpoint, including the tenant
GUID. The auth module logs no token, password or code, as its own notes promise.

On performance: the per-message path is already tight — the state push is gated on something
having changed, and the snapshot handed to entities is cheap. The codec is 2.4 µs per decode.
No entity property computes a time-varying value, so Home Assistant's equality check really
does suppress redundant recorder writes. `_recent_messages` is a bounded deque.

On maintainability: `runtime_cutoff.update()` is long and stays long — it is a linear decision
funnel where every rejection is journalled with its reason, which is the shape safety code
should have and the thing that makes "why did it not fire" answerable. The 28 constants that
nothing references are a reverse-engineered protocol catalogue, including the hub's LAN API
with its firmware version recorded; deleting them would discard findings not recoverable from
the code. And every one of the ten comment references to private symbols was checked by hand:
all ten exist.

**Tests: 152 → 161**, each new one verified failing against the commit before its fix.

**Upgrading:** update through HACS and restart Home Assistant. No entity ids change. If you
have been attaching `home-assistant.log` to issues, this is a good moment to know that the
ordinary log is meant to be free of device ids — but that turning on either debug logger puts
them there deliberately, and they stay until it rotates.
