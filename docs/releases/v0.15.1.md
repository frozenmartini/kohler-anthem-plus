Six bugs from a code review. **Three of them shipped in the last two days** — the cost of a
fast release cadence, found the way it should be.

## Crashes

**A malformed `warmUpState` aborted setup.** `apply_rest_state`'s own docstring promises that
"every container is type-checked before it is walked", and this was the one that was not: `or
{}` rescues a null but hands a list or a string straight through to `.get`. Both call sites
catch only `KohlerError`, so an `AttributeError` here failed setup with a traceback — exactly
the failure 0.10.0's guards were added to prevent.

**An MQTT `outlets` value that is not a list.** The REST path guarded this; the MQTT path did
not, though the comment explaining why sits in the file. A string `"110"` indexes positionally
into truthy characters and reads as **every outlet running** — wrong state, silently, with no
error. An int raises `TypeError` on `len()`, and that shape is not hypothetical:
`docs/hub/cloud_api.md` records Kohler serving `"outlets": 2` as a *count* elsewhere in the
same API.

## The cloud-connection quiet timer died on a quiet shower

`_last_gcs_at` is `None` until the valve's first MQTT message, which on a push-only
integration can be hours — this module's own notes record benign silences of 12 and 35 hours.
The three-hour timer subtracted from it unguarded, and the `TypeError` escaped **after**
`_quiet_cancel` was nulled and **before** either re-arm. So trigger B stopped for the life of
the coordinator: the same "fires once and never re-arms" failure the code comments describe
for an earlier bug, through a different door.

Silence since setup is precisely what that trigger exists to ask about, so it now runs the
check rather than skipping it.

## Every valve was seeded twice

0.9.0 added a concurrent `asyncio.gather` to replace a serial seeding loop — and left the loop
in place. Both ran on every setup, every MQTT reconnect and every manual refresh: double the
REST traffic the change existed to reduce, and two `async_seed` coroutines for one valve
interleaving over the same state objects.

## The reconnect reseed outlived an unload

The only `async_create_task` in the coordinator with no reference kept, and the longest-running
— `_async_seed_state` is a dozen REST round trips. A reload inside that window left it awaiting
HTTP against a coordinator Home Assistant had already discarded, ending in a config-entry write
and a state push into entities that no longer existed. That is the hazard
`Valve._background_tasks` was built for; the coordinator's own task was left out of it. It is
now held and cancelled first on shutdown.

## Blocking file I/O on the event loop (new in 0.15.0)

`ReportLog.note`, added yesterday, opened files directly: `os.makedirs`, a README write, a
directory listing and an `open()`. `write()` gets away with that because paho calls it on its
own network thread; `note()` does not, because the cutoff detector and the warm-up watcher both
run on the loop, where blocking calls are an error in Home Assistant.

The sibling `CutoffDebugLog` had already solved this — `note()` never opens, raises
`wants_open`, and the caller schedules `prepare()` in an executor. `ReportLog` now does the
same.

## Reviewed and found clean

The valve codec was exercised exhaustively rather than read: temperature round-trips exactly
across all 489 encodable values, clamps correctly at both ends, and all 3,912 preset
temperature/outlet combinations survive `encode_preset_word` → `check_preset_word`. The
run-time cutoff — the one feature that can turn water **on** by itself — was checked
specifically for restart-when-it-should-not paths and none were found.
