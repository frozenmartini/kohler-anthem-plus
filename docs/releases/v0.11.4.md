Corrects the explanation shipped in 0.11.3. The code was right; the reasoning printed beside

## `outlets_agree: false` means a **lost write**, not a per-outlet setting

0.11.3 reported that outlets can be configured with different run times. **They cannot.** The
Konnect app offers a single master duration, and the valve stores that same number on every
outlet's record.

What the capture actually showed, read across the full history rather than one file:

| | Rainhead | Showerhead | Handshower |
| --- | --- | --- | --- |
| 08:38 | 3600 | 3600 | 3600 |
| 15:22 | **1800** | 3600 | **1800** |

All three agreed, then two changed and one did not. That is a 60→30 minute change where one
write was lost — and it matches the API's documented behaviour exactly: there is no list form,
so the app writes **one call per outlet**, each carrying the same `maximumRuntime`, and stops
at the first failure. `docs/gcs/api.md` has warned that "a failure mid-loop leaves outlets in
mixed state" since the decompile.

The app keeps showing 30 minutes, because the app shows the value it sent.

**Nothing about the behaviour changes** — reporting the shortest is still right, and for a
better reason: with a stale outlet in the mix, the lower value is the one the setting was
moving toward, as well as the soonest the water can stop. What changes is that
`outlets_agree: false` is now documented as **a fault you can repair**: re-save the duration
in the Konnect app and it rewrites every outlet.

The run-time cutoff's handling of mixed zones also turns out to be right for a stronger
reason than originally written: the valve may genuinely enforce either number, because its
outlets really are holding different ones.
