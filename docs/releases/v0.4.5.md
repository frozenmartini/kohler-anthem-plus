> **What you will see right after updating.** Nothing about how the shower runs has changed —
> this release is about knowing whether the integration is still talking to Kohler, and saying
> so honestly.
>
> **Two diagnostic entities are renamed.** `Cloud Connection` becomes **Valve Reachable
> Online** on a valve and **System Controller Reachable** on a controller, because one name for
> two different questions was the thing people kept misreading. **Entity IDs do not change** —
> the rename is the display name only, and history, dashboards and automations that reference
> the entity ID are untouched.
>
> **New diagnostic entities appear**, all hidden or disabled by default: **Connection Last
> Checked** on each device, and **Valve Connected to System Controller** on a controller. Unhide
> them from the device page if you want them.
>
> **Your log gets quieter.** A restart or a reload no longer announces that connectivity
> recovered — see *Fixed*, below.

**Added — the integration now tells you *which* connection is broken.** "Offline" was one word
covering three different failures, and they need different responses. There are now three
answers, and the combination is the diagnosis:

| Diagnostic | What it answers |
|---|---|
| `MQTT Connection` | Is **our** push subscription to Kohler up? Account-wide |
| `Valve Reachable Online` / `System Controller Reachable` | Is **that device** reachable? Per device |
| `Valve Connected to System Controller` | Is the controller's **physical valve port** linked? |

Everything unavailable at once is your internet or Kohler's cloud. One device unavailable is
that device. A valve that is reachable but not linked to its controller is a wiring or pairing
problem, not a network one. The
[user guide](https://github.com/frozenmartini/kohler-anthem-plus/blob/main/docs/user_guide.md#when-a-device-drops-off-the-cloud)
walks through each case.

**Added — `Connection Last Checked`.** A timestamp sensor on each device, saying when that
device's reachability was last verified. It exists because `Reachable Online` holds its last
answer through a failed request rather than flipping to "unreachable" on one bad call — which
is the right behaviour, but it means that during an outage the entity can read *reachable*
while being hours stale. The timestamp is what tells you which it is. It stays available while
its device is not, since that is exactly when you want it.

**Added — recovery that backs off instead of hammering.** Checks run after 1 minute, then 2,
then every 5; after an hour, every 15 minutes; after a day, hourly. MQTT gets one immediate
reconnect attempt first. Cloud failures share an account-level gate so twenty entities cannot
each start their own retry, and a server `Retry-After` is honoured. A device push or a manual
refresh accelerates recovery. Rejected credentials suspend retries and ask you to sign in
again rather than looping.

For a controller that the cloud says is unreachable, one local `get_hub_version_info` read can
tell a locally-alive controller from a genuinely dead one. It uses the discovered `.local`
hostname, a three-second timeout and no redirects. **No PIN, no sign-in, no local control and
no configuration write is involved**, and a local success does not re-enable cloud controls.

**Added — connectivity events in the Report Log.** Turning the switch on now captures the
connectivity trail in the same file, on the same clock, as the raw MQTT and the cutoff and
warm-up decision records. Enabling it mid-outage records the current baseline first, so the
capture is readable from the start rather than beginning mid-story.

**Changed — the package layout is now the standard HACS one.** The component moved from the
repository root into `custom_components/kohler_anthem_plus/`, and `content_in_root` is gone
from `hacs.json`. HACS handles the move on update; there is nothing to do.

**Changed — what an outage makes unavailable.** An explicit disconnected answer, or a
device-offline response to a command, makes that device's controls and operational readings
unavailable. A *failed request* does not: it preserves the last answer with `stale` and
`last_error` set, or reports unknown if there has never been an answer. MQTT loss takes
cloud-controlled entities across the account. Diagnostic answers and Home Assistant's own
preferences stay readable throughout — which is the point of the entities above.

Disabling a diagnostic entity does not disable recovery. The coordinator owns the watches.

**Fixed — a restart no longer reports a recovery that never happened.** Every restart, and
every reload, logged `connectivity recovered` at WARNING for each device — landing in Home
Assistant's *error originated from a custom integration* panel — for devices that had never
gone anywhere. On an unlucky start, where the first connection attempt failed before
succeeding, `MQTT connection recovered` appeared too.

Both came from reading the retry backoff as proof an outage had happened. It is not: a freshly
started watcher arms that backoff before its first check, and the first MQTT connection failing
once arms the other. The rule now is that **a recovery is announced only if the loss was
announced** — one warning when something goes, one when it comes back, and silence when
nothing was ever wrong. The same gate applies to the connectivity record in the Report Log,
which was making the same false claim in the evidence.

Nobody restarting Home Assistant expects their cloud integrations to report that the
connection came back.

**Fixed — one sign-in prompt instead of several.** Kohler's identity provider rotates the
refresh token every time it is used, so two calls refreshing at once invalidated each other and
could ask you to sign in again for no reason. Overlapping calls now redeem the token once and
share the result.

**Fixed — warm-up no longer gets stuck unknown.** If the first read after setup came back with
no warm-up state in it at all, that state stayed unknown until something else happened to
refresh it. It is re-read now. A normal start, where the first read answers, costs nothing
extra.

**Upgrading:** update through HACS and restart Home Assistant. Nothing to reconfigure. Two
diagnostic entities change their display name and keep their entity IDs; new diagnostic
entities appear hidden or disabled. If you had `Cloud Connection` on a dashboard by its
friendly name, the label changes; by entity ID, nothing does.
