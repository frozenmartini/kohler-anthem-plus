**`Water Used Today` and `Water Used This Week`.** Both from Kohler's own usage history, both
enabled by default — and the probe that made them possible also closed a question this repo
had answered wrongly twice.

## What the probe actually found

The owner ran `probe_usage` on 2026-09-11. The result was the opposite of what the previous
release predicted, and better:

| Interval | Range | Result |
|---|---|---|
| `MONTH` | 400 d (13 buckets) | ✅ 200, in all three date formats |
| **`DAY`** | **14 d (15 buckets)** | ✅ **200** |
| `WEEK` | 400 d (~57 buckets) | ❌ 400 |
| `WEEK` | 90 d (~12 buckets) | ❌ 400 |
| `WEEK` | 28 d (**4 buckets**) | ❌ 400 |
| `YEAR` | 400 d | ❌ 400 |

**The row-cap theory was wrong.** 0.16.3 argued that `WEEK` had only failed because 400 days
asks for ~57 buckets, and predicted a short range would work. It does not: `WEEK` is refused at
**four** buckets while `DAY` is served at fifteen in the same run. Result size is not the
constraint — this endpoint does not take `WEEK` for a GCS valve at all.

**And `DAY` — never asked before this probe — works.** That is the better answer, because
seven daily buckets are a week. One interval covers both sensors.

**Cross-checked before anything was built on it**: the daily buckets for 2026-09 summed to
exactly **465 L**, the figure the `MONTH` call reported for that month in the same run. Same
unit, same window, same data. That is what rules out a plausible-looking series that means
something else — the mistake `totalVolume` has already cost this project once.

## The two sensors

**`Water Used Today`** — water since local midnight. **`Water Used This Week`** — the last
seven days including today, as a **rolling window**, with a `per_day` attribute carrying the
breakdown. Not a calendar week: `WEEK` is refused, and a rolling week answers "how much have we
used lately" without depending on where Kohler would have put the boundary.

Both report in the account's unit, both are `TOTAL` rather than `TOTAL_INCREASING` (each resets
by design, and calling that a meter reset would inject phantom water into long-term
statistics), and both read `unknown` rather than `0` before a series arrives — because zero is
a claim, and "no data yet" is not the same as "no water used".

On the owner's account at the moment of writing: **10.8 gal today, 79.8 gal over seven days.**

## Refreshed when a shower ends — not on a clock

This integration has no polling loop (`SCAN_INTERVAL` is `None`) and this release does not add
one. Usage only moves while water runs, so the re-read is tied to the valve's own
running → stopped edge. **A day when nobody showers costs no cloud calls at all.**

There is a 90-second delay first, and it is not politeness: Kohler aggregates a session
server-side *after* the valve reports it closed, so reading the instant the water stops returns
the day's total **without** the shower that just finished — precisely the reading someone would
go and check. A burst of stop-messages during a single wind-down collects one read, not
several.

Startup cost is unchanged in wall-clock: the daily series is fetched alongside the monthly one
rather than after it, so the seed is still **two round trips deep** despite now making six
calls.

## What this endpoint's 400 actually means

Twice now a feature has been called unsupported here on evidence that could not support it:
fifteen camelCase candidates in 0.7.8, and `WEEK`-at-one-range in 0.16.2. Both times a single
generic 400 stood in for several unrelated causes.

`docs/gcs/api.md` now records the rule rather than the conclusion: **a 400 from `gcs-usage`
means "something about this request was wrong", never "this feature does not exist".** The way
to tell them apart is to vary one thing at a time — which is what asking `WEEK` at three ranges
did, and what asking `DAY` at all should have done months ago.

**Tests: 164 → 170**, including the real probe response as a fixture, the metric path, the
empty-series case, and the running → stopped edge with its debounce.

valve, enabled by default; nothing existing changes.
