**Three settings the Konnect app has always let you change are now changeable here.** Max
Temperature, Max Shower Duration and Default Temperature stop being readings and become
controls.

## The three

| Entity | Type | Range |
|---|---|---|
| **Max Temperature** | number | 92–118 °F — the app's own range |
| **Default Temperature** | number | 59 °F up to **whatever the scald limit currently is** |
| **Max Shower Duration** | select | 15 / 20 / 25 / 30 / 45 / 60 minutes |

All three sit in the **configuration** category, because that is what they are. A read-only
copy of a setting someone can change from two other surfaces was the odd one out.

**Default Temperature's ceiling moves with the scald limit.** Lower Max Temperature to 104 °F
and this entity's maximum follows it down. The app bounds it the same way, and it is the only
bound that stays correct — a fixed ceiling would let someone set a starting temperature the
valve will not honour.

**Max Shower Duration is a select, and that is a finding rather than a style choice.**
`docs/gcs/api.md` had left open whether 3600 s is a ceiling or the top of an allowed list: the
app's picker is curated — it skips 35, 40, 50 and 55 minutes, all legal multiples of 300 s
that no shipped picker can produce, and whether the valve would take one is **untested**.
Offering exactly what the app offers claims only what is known; a slider would imply the gaps
are reachable. 3600 s being live-verified writable is what makes 45 and 60 real options rather
than guesses.

## Every write is verified, and a partial write says so

`writeoutletconfig` has **no list form**: one call per outlet, each carrying that outlet's
entire record, each issued only after the last returned 2xx. A failure part-way therefore
leaves the valve holding the new value on some outlets and the old one on others — and that is
not hypothetical. It is exactly what produced the `outlets_agree: false` this integration
already reports, caught on real hardware in September.

So after the chain completes, this **reads the value back**. A 201 from that endpoint means
*accepted for delivery*, never *applied* — the response carries no echo of the value, and the
Konnect app performs no verification at all.

* **The valve ignored it** → an error saying so, rather than a dashboard showing a change that
  did not happen.
* **It failed part-way** → an error naming which outlets took the new value, and that
  re-saving rewrites every one of them.

⚠️ **The read-back waits 30 seconds first, and that is not padding.** `gcsadvancestate` is a
cloud document that updates only once the device reports; a read about a second after a 201
still shows the **old** value. Verifying too early is precisely how a working write looks like
a device-side limit — a mistake this project has already made about this API more than once.

## What had to be fixed before any of this could be written

🚨 **`writeoutletconfig` replaces an outlet's whole record**, and three of its keys were never
read: `outLetFlags`, `minimumOutletTemperature`, and `defaultOutletTemperature` — the last
being the very field behind Default Temperature.

Writing would have meant inventing all three, and one of them sits beside the scald limit. So
they are now parsed, reported in diagnostics, and **`None` when absent rather than `0`** —
zero is a legal-looking value for each, and echoing a spurious zero back would silently reset
the record the write meant to preserve.

**Any unread field refuses the write** rather than guessing at it. A Default Temperature above
the scald limit is refused before it reaches the valve.

The corroboration that `defaultOutletTemperature` is the app's Default Temperature: the
minimum beside it parses to exactly **59.0 °F**, which is the floor the app offers for that
setting.

## Two things worth knowing

**The read-only sensors stay.** `Max Temperature` and `Max Shower Duration` still exist as
diagnostic readings, with their original unique ids. The new controls have their own, because
reusing an id would swap one entity for another in every dashboard already pointing at it.

⚠️ **Konnect 3.0.1 misreads any duration above 30 minutes.** Its picker snaps the device's
value into 15–30 before choosing a wheel index, so a valve set to 45 or 60 displays as 25 —
and one tap of Save silently writes 1500 s. A vendor defect, fixed in 3.0.5. Choosing a longer
duration here is safe for the valve and safe in a current app; only an out-of-date one would
quietly undo it. The entity publishes `long_duration_app_warning` so an automation can see it.

Also closed this release: whether a **GCS-only install** populates `gcs-configuration`'s
structural fields — recorded as "exactly the case no one has been able to check". A
controller-free account reports all seven unpopulated, so the controller was never the reason.
The topology already comes from `gcsadvancestate`, so nothing changes but the record.

**Tests: 172 → 180**, covering the write body's wire units and its write-side key spellings,
every refusal, the verification, an ignored write, and a partial write.

**Upgrading:** update through HACS and restart Home Assistant. Three new entities appear on
each valve; nothing existing changes or moves.
