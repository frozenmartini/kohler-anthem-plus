**Removed — the Shower water-heater entity that 0.5.0 added.** It duplicated the Zone 1
Temperature number without adding anything on a single-zone valve: both read the same
expression on the same valve word, so the card's dial and the number were two controls for
one setpoint. The card also rendered as `off 103°`, which reads like a current temperature
and is not one — that is the operation mode beside the *setpoint*, since this hardware
measures nothing and the entity's `current_temperature` was always empty. Collapsing four
controls into one card only pays off on a two-zone valve or a fresh install; alongside the
existing number and the Shower switch it was a third way to do what was already there.

If you installed 0.5.0, the entity will be left behind in the entity registry reading
unavailable. Remove it from the valve's device page, or leave it for the next registry
cleanup.

**Added — outlet type, and a name for it where the code is confirmed.** The valve reports a
type code per outlet in `outLetType`, and the integration was discarding it. It is the only
per-outlet identity the hardware reports — what tells a rainhead from a tub filler on an
install whose outlets are otherwise just numbers. Every outlet switch now carries
`outlet_type`, and `outlet_type_name` beside it where the code's meaning is established:

| Code | Fixture | Where it comes from |
|---|---|---|
| `1` | Handshower | Kohler's own API documentation |
| `11` | Showerhead | Kohler's own API documentation |
| `21` | Tub Filler | Documentation, and matches the owner-confirmed tub filler in the capture corpus |
| `52` | Showerhead | Owner-confirmed, K-28210 |
| `62` | Rainhead | Owner-confirmed, K-28210 |

The two new rows come from an install whose zone 1 reads Rainhead / Showerhead / Handshower
across outlets 1-3. Its third outlet is type `1`, independently reproducing the documented
`1 = handshower` — which is what makes the other two credible rather than merely plausible,
since it shows the id-to-type order holds on a second, unrelated system.

**Codes 38 and 39 are deliberately left unnamed.** Both appear in the corpus and neither has
ever been confirmed against a physical fixture, and the two devices disagree about the same
outlet — id 4 is `39` to the valve and `38` to the controller. An unrecognised code is
published as a bare number with no name, so a missing name reads as "not known" and never as
a wrong fixture. If your outlets show a code that is not in the table above, please open an
issue saying what the fixture actually is.

**These are fixture types, not the names you typed into the Konnect app.** No outlet name
string is transmitted anywhere in the captured API surface, so a rename made in the app
cannot be read back.

**Added — a Firmware sensor, and the valve's configuration record.** The integration had
never called `gcs-configuration` at all. It does now, once at the first seed —
installation-time data that cannot change while Home Assistant runs, so a reconnect does not
spend a call on it, and a failure is logged and ignored rather than breaking setup. The
firmware version it carries is published as a diagnostic sensor, disabled by default: it
matters when comparing behaviour across firmware versions in a bug report, not day to day.

The same read settles a question this project has had open. On the reference install — a
valve wired to an Anthem Plus controller — every structural field in that record comes back
null, because such a valve reports its configuration through the controller, and whether a
**controller-free** install populates them has never been captured. Diagnostics now carry a
`configuration` block reporting which keys arrived, so a report from such an account answers
it. It reports key *names*, not their contents: the structural blocks describe someone's
plumbing, and the question only asks which of them exist.

**Added — an API probe log, for seeing what Kohler actually sends.** The diagnostics report
describes what the integration *understood*. When the question is what arrived — including
fields no code path reads — every REST call now logs its endpoint, status and full response
body under one debug logger. Off by default, no restart needed, from Developer Tools →
Actions:

```yaml
action: logger.set_level
data:
  custom_components.kohler_anthem_plus.anthem_plus.client: debug
```

Set it back to `info` to stop. The MQTT half of the same picture was already capturable
through the raw-capture logger, so between them every byte the integration receives can now
be seen — which is how this project's endpoint documentation was written in the first place.

**Credentials are redacted** before anything is written: the mobile-settings call returns a
short-lived IoT Hub password, and any key whose name looks like a password, token, key or
secret has its value replaced. Redaction keeps the structure — the key stays, so a redacted
field still tells you it was there. Note that a raw log **does** carry device ids and serial
numbers, which the diagnostics report redacts; skim one before attaching it to an issue.

**Changed — the Favourite picker says why it is empty.** An `Off`-only dropdown is
indistinguishable from one that failed to load, and the difference matters, because usually
nothing is wrong. A valve has **ten preset slots**, slot 1 is the mandatory default shower —
run by the Shower switch and hidden from the list, exactly as the Konnect app hides it — and
the other nine are empty until somebody creates a favourite. So a valve nobody has
customised correctly offers nothing, and now says so in a `no_favourites_reason` attribute
naming both the cause and the fix. Create a favourite in the Konnect app and it appears with
no reload.

**Fixed — the preset counts in diagnostics could not be read straight.** `selectable` counts
slots *before* the hidden default-shower slot is removed, while the dropdown offers what is
left *after* — so a valve with no user favourites reported `selectable: 1` and offered
nothing, which reads as a bug and is not one. This was mistaken for exactly that while
0.5.0 was being written, and the release notes for it carried the wrong explanation as a
result. The report now carries `offered` beside `selectable`, plus `hidden_ids_present`.

**Corrected — 0.5.0 said experiences were why the picker looked empty.** They are not.
Hiding the default-shower slot is, and a valve with a single slot and no experiences at all
is equally empty. Experiences are still named in the entity's attributes with a note saying
why they cannot be started — that part stands — but they were never the cause.

**Upgrading:** update through HACS and restart Home Assistant. No config changes to make.
Outlet switches gain their type attributes immediately; the Firmware sensor is diagnostic
and disabled by default, so enable it from the valve's device page if you want it. The only
entity removed is the water heater from 0.5.0, described above.
