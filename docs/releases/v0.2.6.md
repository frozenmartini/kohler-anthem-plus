## New: know when the valve drops off Kohler's cloud

The Anthem valve loses its cloud connection on its own, and comes back only when it is
physically power-cycled. Until now nothing in Home Assistant told you that had happened — the
controller, the account and the MQTT stream all stay healthy, so nothing goes red and every
valve entity simply freezes on its last value with no explanation. This is the state behind
"the Konnect app says my valve is offline".

**`binary_sensor.anthem_valve_cloud_connection`** answers it directly, and is **enabled by
default** — the other valve diagnostics answer *is this integration well*, this one answers
*is the shower going to work*.

It does not poll. `SCAN_INTERVAL` is still `None`, and the sensor is driven by two push
events that decide when a single REST read is worth making:

- **A contradiction.** The controller reports a zone ON while the valve stays silent for 60
  seconds. Across a 19-day capture, 435 of 437 zone-ON messages had a valve message within
  60 s — the two that did not were the outage itself.
- **Three hours of valve silence.** Covers valve-only accounts, and the stretches the
  controller sleeps through.

At most one read every 30 minutes either way, and the field is also taken from the
`gcs-state` reads the integration already makes at setup, on reconnect, and on every warmup
read-back — those cost nothing and never consume the cooldown.

Silence alone is never the verdict, because it cannot be: over that same capture the longest
provably benign silence was 12 h 02 m and the one real outage was 12 h 22 m. Twenty minutes
apart. No threshold separates them, so silence only decides *when to ask* — the answer always
comes from `gcs-state`'s `connectionState`.

A failed read is not a verdict either. "We cannot reach Kohler" and "Kohler cannot reach the
valve" are different faults, so an error leaves the previous answer standing and reports
itself in `last_error` instead.

Attributes carry the working: `connection_state`, `last_checked`, `checked_because`, `checks`,
`last_error`, `cloud_last_connected`, `seconds_since_valve_message`, `contradiction_watch`.
`checked_because` matters more than it looks — an answer taken while a shower was running is
much stronger evidence than one taken because the valve had been quiet overnight.

## New documentation: running both systems together

A first-generation Anthem valve and an Anthem+ controller can be run at the same time, and
that is the configuration this integration was built against. It was undocumented. The full
guide now has **[Using both together](https://github.com/frozenmartini/kohler-anthem-plus/blob/main/docs/user_guide.md#using-both-together)**.

The hardware first, because nothing else makes sense without it. The first-generation
touchscreen is an HID with a screen — **no Wi-Fi, no Bluetooth, no radio at all** — and the
valve is the part holding the network connection. Anthem+ is a second-generation touchscreen
attached to a Linux system controller that every accessory hangs off. The valve has two
ports, so both can be attached at once, and the controller is then a client of the valve on
one port and a cloud device in its own right over Wi-Fi. That is why one shower appears as
two Home Assistant devices.

Also covered:

- **Five entity names exist on both devices** — `Shower`, `Favourite`, `Status`,
  `Zone N Temperature`, `Zone N Outlet M`. Two differ in *type*, not just device, so "the
  entity I meant to set is read-only" means you have the controller's copy.
- **Each device has its own default outlets and its own favourites list**, stored in
  different boxes. The same press of the dial on two screens in one room can start two
  different showers.
- **The one hard requirement.** The valve raises its Wi-Fi access point only when told to
  from a first-generation screen. An Anthem+ touchscreen plugged straight into the valve does
  nothing. Whatever the final wiring, a first-generation screen is needed at least once.

## Corrected in the documentation

- **Music needs a separate Kohler amplifier, K-30319.** It is not built into the controller.
- **Lighting is not blocked for want of bulbs.** Sengled wound down as a company but the
  bulbs are still sold. The real gap is that no Sengled bulb has ever been tried on this
  hardware — the one attempt used Philips Hue and did not pair.
- Music, lighting and steam being read-only is the limit of what **Konnect** exposes, not
  what the hardware can do.

## Under the hood

- HACS and hassfest validation now run on every push, on pull requests, and nightly. Both
  pass. hassfest needs the integration checked out under a directory named for the domain,
  since this repository sets `content_in_root`.
- Artwork nothing referenced has been removed.

## Upgrading

Nothing to do. Update through HACS and **restart Home Assistant** — the new sensor appears on
the Anthem Valve device afterwards. No configuration changes, no entities renamed or removed.
