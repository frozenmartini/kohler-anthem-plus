> **If you are on 0.4.5, update.** On 0.4.5 the integration cannot load at all — not only when
> you add it, but at every Home Assistant start. If it is installed and working for you right
> now, that is because Home Assistant has not restarted since the update. This release fixes
> it, and nothing you have configured is affected.
>
> **On 0.4.1 or earlier you were never affected** — the fault arrived in 0.4.5.

**Fixed — the integration could not load on 0.4.5.** Adding it failed with *"Config flow could
not be loaded: {"message":"Invalid handler specified"}"*, and the log showed:

```
Error occurred loading flow for integration kohler_anthem_plus: cannot import name '_dev'
from partially initialized module 'custom_components.kohler_anthem_plus'
(most likely due to a circular import)
```

The integration has a seam for a development-only package that ships in no release, and it
tolerated that package's absence by catching `ModuleNotFoundError`. That is the wrong
exception: importing a missing name from a package that is still initialising raises plain
`ImportError`, the parent class, so the error escaped and took the whole package import down.
Every install without that package — which is every install but the author's — hit it, which is
also why it was not caught before release.

Reported and diagnosed by [@omnintro](https://github.com/omnintro) in
[#8](https://github.com/frozenmartini/kohler-anthem-plus/issues/8), who found the line and the
fix. Thank you — this one needed an outside pair of eyes by construction.

There is now a release-shape check that imports the published tree with the development package
absent, so this class of fault cannot reach a release again.

**Fixed — a token response that is not JSON no longer strands setup.** When a gateway in front
of Kohler's sign-in answers with an HTML error page instead of JSON — a 502 or 503 — the token
request raised a JSON decode error. That is neither an authentication error nor a connection
error, so nothing caught it, and the config entry stopped at *Failed to set up* with no retry.
It is now classified: a non-200 with an unreadable body is treated as the service being
temporarily unwell and **retried**, while a 200 with an unreadable body is treated as an
authentication failure. A transient cloud problem no longer looks like a broken credential.

**Changed — "No pausing warm-up" is no longer marked beta.** The option that keeps the shower
running when the valve's warm-up ends has carried a *beta* label since 0.3.0. It is dropped:
the action it belongs to has been in use without trouble. The measurements behind it are
unchanged and still in the
[user guide](https://github.com/frozenmartini/kohler-anthem-plus/blob/main/docs/user_guide.md),
which records how many valves it has run on — please still say how it behaves on yours.

⚠️ **The field's label changes** from *No pausing warm-up (beta)* to *No pausing warm-up*. If
you use it in an automation, nothing breaks: the underlying option is `keep_on_after_warmup`
and it has not changed. Only the label you see in the editor does.

**Changed — the Custom shower form is about half as long.** Its descriptions ran to fifteen
lines on a phone, and the service's own blurb restated the *No pausing warm-up* field that sits
a few rows below it in the same form. The duplication is gone and each description says its
piece once. Nothing about what the action does has changed.

**Upgrading:** update through HACS and restart Home Assistant. Nothing to reconfigure, and no
entity IDs change. If you are on 0.4.5, do this rather than leave it — see the note at the top.
